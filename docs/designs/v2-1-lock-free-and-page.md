# Version 2.1.0: lock-free lookups, allocation-free keys, occupancy, union, new page

Status: revised after Goldfish review (see "Review record"). Two deliveries:
**A** the library, released as 2.1.0 for all five packages
(`M5.BloomFilter`, `M5.BitArraySerialization.Json`,
`M5.BitArraySerialization.ProtoBuf`, `M5.BloomFilter.Serialization.Json`,
`M5.BloomFilter.Serialization.ProtoBuf`); then **B** the GitHub Page, merged
only after 2.1.0 is on nuget.org so the page never describes an unpublished
package.

## Problem

Version 2.0.1 is correct but slow where a Bloom filter is used most: single-key
lookups on a shared filter.

1. `BloomFilter` guards a `BitArray` with one lock. Every `Contains` takes it, so
   concurrent readers run one at a time.
2. Every single-key call allocates: `ComputeHash` returns a new `int[]`, string
   overloads allocate a UTF-8 `byte[]`, and numeric overloads box the value and
   allocate a `byte[]`.
3. A caller cannot ask a filter how full it is. Overfilling is the usual way a
   filter goes wrong, and `Statistics.P` only reports the design estimate.
4. Two filters built with the same settings cannot be merged, so a filter cannot
   be built in shards or on several machines and then combined.
5. The GitHub Page describes the library but proves nothing. Its demo is a
   64-bit toy with a teaching hash that is not the library's hash.

## Non-goals and fixed constraints

- **No hash, key-encoding or persisted-format change.** Format version stays 2.
  Every 2.0.x payload loads in 2.1.0 and every 2.1.0 payload loads in 2.0.x.
  The sixteen frozen vectors in `HashVectorTests` pass unmodified, and new
  fixtures generated by the published 2.0.1 packages pin the rest.
- **No breaking API change.** Nothing is removed or renamed. No member is added
  to `IBloomFilter`, `IImmutableBloomFilter` or `HashFunction`, so existing
  implementations, subclasses and mocks behave exactly as before.
- **No weakened guarantee.** Snapshots stay consistent; batch calls keep their
  enumerate-first behaviour.
- No delete, no counting filter, no intersection, no new serializer, no new
  runtime dependency.
- Batch overloads are not a performance target in this release.

## Core changes (`M5.BloomFilter`)

### C1. Lookups stop taking the lock

`BloomFilter` replaces `BitArray` with `int[] _words` of length
`(int)(((long)m + 31) >> 5)`. Bit `i` is `_words[i >> 5]` bit `i & 31`, the
layout `BitArray` uses, so exported bits and serialized bytes are unchanged.

- **Writers keep the lock** (`Add`, batch `Add`, `UnionWith`). Inside it they OR
  bits into the words with plain writes; only one writer runs at a time, so no
  update is lost, and leaving the lock publishes the writes.
- **Lookups take no lock.** A lookup issues one `Volatile.ReadBarrier()` and
  then reads the words it needs with ordinary reads.
- **Snapshots keep the lock** (`HashBits`, `ToImmutable()`), exactly as in 2.0:
  a snapshot is the state after some whole number of completed write calls.

`ReadOnlyFilter` stores the same `int[]` and never writes it after construction.
Its two `BitArray` constructors copy with `hashBits.CopyTo(int[], 0)` and then
clear any bits at or above `m` in the last word. Its `IBloomFilter` constructor
copies from `filter.HashBits` the same way (for the built-in filter that export
is taken under the lock).

Export builds `new BitArray(m)` and copies the word bytes into
`CollectionsMarshal.AsBytes(bits)` (byte-swapping per word on a big-endian
runtime). It does not use `new BitArray(int[])`, which .NET 10 rejects above
67,108,863 words and would therefore fail for `m > 2,147,483,616`.

| Invariant | Why it holds |
|---|---|
| Inserted keys never become absent | Bits are only OR-ed in, by one writer at a time. |
| A lookup after a completed `Add` sees it | Leaving the lock is a full fence; a lookup's acquire barrier orders its reads after whatever told the caller the insertion had finished. |
| Snapshots are consistent and own their bits | Taken under the writer lock into new storage. |
| Duplicate insertion is idempotent | OR is idempotent. |

What changes for callers: a lookup that overlaps an insertion no longer waits for
it and may observe some of that insertion's bits. `docs/usage.md` already says an
overlapping query may come before or after the insertion; it will now also say
lookups are lock-free and that a batch insertion is atomic for snapshots but not
for overlapping lookups. Parallel bulk loading is served by C6: fill one filter
per worker, then union them.

### C2. Allocation-free hashing for the default strategies

No public hashing API changes. `HashFunction` gains

```csharp
internal virtual bool TryComputeHash(ReadOnlySpan<byte> data, int m, Span<int> positions) => false;
```

`Murmur3KirschMitzenmacher` and `Murmur3` override it, and each override first
checks `GetType() == typeof(...)`. A user subclass of either class therefore
returns `false` and is hashed through its own `ComputeHash(byte[], int, int)`
override, exactly as in 2.0. The Murmur3 core gains a `ReadOnlySpan<byte>`
overload; the existing array core delegates to it. All other strategies return
`false` and run the 2.0 code path unchanged, with the same calls and the same
allocations.

The built-in filters hash into `stackalloc int[k]` when `k <= 128`, otherwise
into a new array, when `TryComputeHash` succeeds.

For `Murmur3KirschMitzenmacher` position `i` is `(h1 + i * h2) mod m`. The span
core produces it by stepping: start at `h1 mod m`, add `h2 mod m`, and subtract
`m` when the sum reaches it, with no branch. Both residues are below
`m <= 2^31 - 1`, so the sum fits in 32 bits and the result is identical to the
64-bit division the array method performs. Lookups with that strategy test each
position as it is produced and stop at the first clear bit, using the same
`First`/`Next` helpers as `TryComputeHash`. The writer path tests whether every
bit is already set before taking the lock; an insertion that would change
nothing does not lock.

### C3. Existing single-key overloads get faster without changing meaning

Only when the filter is the built-in `BloomFilter` or `ReadOnlyFilter`:

- `Add(string)` / `Contains(string)`: keys of up to 85 UTF-16 units are encoded
  into a 255-byte stack buffer with `Utf8.FromUtf16`, which replaces unpaired
  surrogates with U+FFFD exactly as `Encoding.UTF8.GetBytes(string)` does; the
  conversion must report completion. Longer keys are sized with
  `Encoding.UTF8.GetByteCount` and encoded into a rented buffer that is cleared
  on return. Null still throws `ArgumentNullException`.
- Scalar `Add`/`Contains` for `byte`, `short`, `ushort`, `int`, `uint`, `long`,
  `ulong`, `float`, `double`, `DateTime`: write the little-endian bytes that
  `Encode(object)` writes, into a stack buffer, without boxing.
- If the strategy has no span core, these overloads build the same `byte[]` as
  2.0 and call the same array method.

For any other `IBloomFilter` / `IImmutableBloomFilter` implementation the
extensions call the interface methods with the same arguments as today.

Unchanged: the `object` scalar overloads, every `AddAsync`/`ContainsAsync`,
every `ComputeHash` extension, and all typed and generic batch overloads
including `All`. `DateTime` keys are `Ticks`, and `float`/`double` keys are
their raw IEEE bits, as before.

A position outside `[0, m)` can only come from a custom `HashFunction`. The
shared storage rejects it with `ArgumentOutOfRangeException` before any bit is
read or written, as `BitArray` did in 2.0.

Batch overloads keep two phases: enumerate every key and compute its positions,
then touch bits. A null element still fails before a batch `Add` changes the
filter, and an enumerator that mutates the filter while being enumerated gets
the same answers as in 2.0. The only batch change is that `Contains` no longer
takes the lock and no longer builds an intermediate `bool[]`. `All` is unchanged.

### C4. New span entry points

```csharp
public static void AddKey(this IBloomFilter filter, ReadOnlySpan<byte> key);
public static void AddKey(this IBloomFilter filter, ReadOnlySpan<char> key);   // UTF-8
public static void AddKey(this IBloomFilter filter, string key);               // null throws
public static bool ContainsKey(this IImmutableBloomFilter filter, ReadOnlySpan<byte> key);
public static bool ContainsKey(this IImmutableBloomFilter filter, ReadOnlySpan<char> key);
public static bool ContainsKey(this IImmutableBloomFilter filter, string key); // null throws
```

Built-in filters take the fast path. For any other implementation the byte
overload calls `filter.Add(key.ToArray())` and the char and string overloads
UTF-8 encode the whole key into a `byte[]` and pass that, so one key is always
one key. The `string` overload exists so that `AddKey((string)null)` throws
instead of converting to an empty span and inserting the empty key.

They are **not** named `Add`/`Contains`. A span overload under the old name
could silently rebind an existing call: `filter.Add(charArray)` binds today to
the generic batch (one key per character), and with C# 14 span conversions a
same-named `ReadOnlySpan<char>` overload could take it as one key and produce
false negatives against a filter built by 2.0.x. A new name cannot change what
existing code means.

### C5. Occupancy

```csharp
public static BloomFilterOccupancy GetOccupancy(this IImmutableBloomFilter filter);

public readonly struct BloomFilterOccupancy
{
    public int SetBits { get; }
    public int TotalBits { get; }                    // m
    public int HashCount { get; }                    // k
    public double FillRatio { get; }                 // SetBits / m
    public double EstimatedFalsePositiveRate { get; } // FillRatio ^ k
    public double EstimatedCount { get; }            // -(m / k) ln(1 - FillRatio)
}
```

One call, one pass. Built-in filters count their words with
`BitOperations.PopCount` (lock-free; a moving estimate while writers run); other
implementations are counted from one `HashBits` export. `EstimatedCount` is the
Swamidass–Baldi estimate and is `double.PositiveInfinity` when every bit is set.
`Statistics` keeps describing the design; occupancy describes the contents.

### C6. Union

```csharp
public static bool IsCompatibleWith(this IImmutableBloomFilter filter, IImmutableBloomFilter other);
public static void UnionWith(this IBloomFilter filter, IImmutableBloomFilter other);
public static ReadOnlyFilter Union(this IImmutableBloomFilter filter, IImmutableBloomFilter other);
```

Two filters are compatible when `M` is equal, `K` is equal, and either both use
the same `HashFunction` instance or both report the same `HashMethod` other than
`Unknown`. Null arguments throw `ArgumentNullException`; incompatible ones throw
`ArgumentException`. The union has every bit either operand had, so every key
inserted in either is present.

`UnionWith` first takes `other.HashBits` (a consistent export for built-in
filters), then ORs it in under the target's writer lock. The target must be the
built-in filter; any other `IBloomFilter` exposes no way to set bits and gets
`NotSupportedException`. The extension lives on `IBloomFilter` because the
built-in class is internal and `FilterBuilder` returns the interface.

`Union` works for any two implementations through `HashBits` and returns a
`ReadOnlyFilter` with the left operand's `N` and `P`. Those are design values for
that geometry, not a description of the merged contents; the XML docs and
`docs/usage.md` say so and point to `GetOccupancy()`.

  a key it already yielded gets the 2.0 answer; `k` = 1.

  absent from a later lookup; sequential adds of A then B never yield a snapshot

  implementation.

  `K` and strategy; `Unknown` strategies with different instances; nulls;
  self-union; foreign target; a source that is being written.

## GitHub Page (delivery B)

Replace `docs/site` content. The page stays static: no build step, framework,
analytics or third-party request. It ships after 2.1.0 is verified on nuget.org.

**What it proves.** The page loads `words.json`, a snapshot of a filter holding
the 172,823 words of the public-domain ENABLE word list, written by this library
with `BloomFilterJsonConverter` (format v2, Murmur3KirschMitzenmacher, 1%
target). A JavaScript port of that hash queries it. The positions shown for a
typed word are the values `ComputeHash` returns in C#, and the page prints the
C# line that reproduces them. A WebAssembly build of the library was rejected:
it needs a build step and a multi-megabyte runtime download for forty lines of
hashing, and the shared vectors below already catch drift.

**How it is drawn.** Bloom published in 1970. The filter is drawn as what it
would have been then: a deck of 80-column, 12-row punched cards, 960 bits per
card. A lookup pulls the cards its positions fall on and shows whether each hole
is punched. A card cannot be unpunched, which is the no-delete rule. The
direction contract is in `.impeccable/surfaces/docs-site-index-html.md`.

**Sections.** (1) header card: claim, word input, install command; (2) the
reader: verdict, seven probes, the cards; (3) "feed it nonsense": 10,000
generated non-words, measured false-positive tally and the strings that got
through, each linkable as `?w=`; (4) sizing calculator using the formulas in
`Statistics.cs`, including the Int32 limit; (5) install and code for 2.1.0;
(6) recorded benchmarks; (7) serialization and the version 2 rebuild rule;
(8) limits; (9) FAQ matching the JSON-LD; (10) MILL5 and Richard Crane.

**Accuracy rules.** The verdicts are "definitely not in the list" and "probably
in the list". Generated non-words are 9–12 letters; the generator is checked
offline against the list so a real entry is not counted as a false positive.
The tally is labelled as measured in the visitor's browser. Every other number
is computed from the loaded snapshot or the sizing formulas. Benchmark figures
come only from `docs/benchmarks.md`.

**Data provenance.** `tools/SiteFilter` (console project, outside the solution,
not packable) builds `docs/site/words.json` from a word-list path. It refuses to
run unless the file's SHA-256 is
`3f16130220645692ed49c7134e24a18504c2ca55b3c012f7290e3e77c63b1a89` and it holds
172,823 distinct lower-case entries, verifies that every entry tests present in
the snapshot it is about to write, and prints positions for fixed words. The
list is not committed. `tools/SiteFilter/README.md` and
`THIRD-PARTY-NOTICES.md` record the source URL pinned to a commit, the hash, the
ENABLE public-domain release notice with a citation, and that `words.json` is a
derived bit array containing no words. The printed vectors are asserted by
`SiteVectorTests` in `M5.BloomFilter.UnitTests` and by the page's start-up
self-check. If the self-check fails the page says the demonstration is
unavailable and hides the "same numbers as C#" claim; it never shows a verdict
from a port that disagrees with the library.

## Risks

| Risk | Mitigation |
|---|---|
| A fast path hashes different bytes or positions than 2.0 | Fixtures generated by the published 2.0.1 packages; frozen vectors unchanged. |
| A user hash subclass is bypassed | Exact-type guard; subclass tests. |
| Stale read under concurrency | Writers under the lock, `Volatile.Read` lookups, stress test. |
| Export fails at maximum capacity or carries stray bits | Logical-length `BitArray`; masked last word; `int.MaxValue` and `m % 32 != 0` tests. |
| JavaScript port drifts from C# | Shared vectors asserted on both sides; visible failure state. |
| Page describes an unpublished package | Page ships only after nuget.org verification. |
| NuGet publish is irreversible | Publish only from the merged `main` commit after CI, oracle `--read` and package inspection. |
