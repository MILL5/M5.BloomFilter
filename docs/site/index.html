        Put one in front of something slow

        A Bloom filter earns its keep in front of a lookup that costs something: a database, a cache miss, a call across a network. Ask the filter first. A no saves the trip. A yes means go and check.

        dotnet add package M5.BloomFilter

        Version 2.2.0 for .NET 10 and 11, source-available under PolyForm Strict 1.0.0, which is not an open-source license.

        using M5.BloomFilter;

var seen = FilterBuilder.Build(
    expectedElements: 1_000_000,
    errorRate: 0.01);

seen.Add("customer:42");
seen.Add(8675309L);

string key = "customer:43";

// A no is certain: skip the database.
if (!seen.Contains(key))
    return NotFound();

// A yes is a maybe: go and check.
var row = await db.FindAsync(key);

        Size your own

        The same arithmetic as Statistics.cs. It assumes the hash spreads keys evenly, so it is a design estimate and not a measurement. Add more keys than you planned for and the false yeses climb; nothing throws.

        Small API. Explicit tradeoffs.

        Build and query

        FilterBuilder.Build(count, errorRate) returns an IBloomFilter; an overload takes one of sixteen HashMethod strategies. Add and Contains take strings, numbers, spans and collections.

        Strings are hashed as UTF-8 and numbers as little-endian bytes, so the same value always lands on the same bits. ComputeHash shows the positions; GetOccupancy() reports how full the filter is now.

        Usage guide

        Snapshots and threads

        ToImmutable() returns a detached snapshot. The companion packages write it as JSON or protobuf with its hash strategy, sizes and format version, so a reader can refuse bits it would misread. words.json, the file behind this page, is one.

        Lookups take no lock; any number of threads can query one filter. UnionWith combines filters built with the same settings. Versions 2.0 and 2.1 read each other’s files; 1.x filters must be rebuilt from their keys.

        Serialization guide

        What to watch

        A yes is a maybe: confirm it against the data that knows. There is no delete; when keys leave your set, build a new filter from the ones that remain.

        Overfilling is silent, so check GetOccupancy(). The error rate assumes ordinary keys; someone choosing keys on purpose can beat it, so never use a filter to authorize anything.

        Questions people ask

        What is M5.BloomFilter?

        M5.BloomFilter is a source-available C# Bloom filter library for .NET 10 and .NET 11. It answers whether a key might be in a set using a compact array of bits instead of the keys themselves.

        Can a Bloom filter give a wrong answer?

        Only in one direction. A positive result means possibly present and can be a false positive. A negative result means definitely absent, provided the same filter, hash strategy and key encoding are used and the bits are intact. Confirm positive results against your source of truth.

        Does an error rate of 0.01 guarantee 1% false positives?

        No. The error rate is a sizing target for the expected number of keys, under the usual assumption that hashes spread keys evenly. Adding more keys than planned raises the rate. GetOccupancy() estimates the current rate from the bits that are actually set.

        Is the demonstration on this page the real library?

        The filter is. It was built by M5.BloomFilter in C# from the public-domain ENABLE word list and saved in the library's JSON format. The lookups run in your browser through a JavaScript port of the library's default hash, Murmur3KirschMitzenmacher, checked against the same test vectors as the C# code.

        Is it safe to use from several threads?

        Yes. Lookups take no lock, so any number of threads can query one filter at once. Insertions and snapshots share a lock. A lookup that starts after an insertion has finished always sees it.

        Can I read filters saved by an older version?

        Versions 2.0, 2.1 and 2.2 read each other's snapshots. Filters saved by 1.x must be rebuilt from the original keys, because version 2 changed hashing; relabelling old bits as version 2 would produce false negatives.
