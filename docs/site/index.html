A filter never turns away a word it was given. What it does, now and then, is wave a stranger through. This deck was sized so that about one made-up string in a hundred finds all seven of its holes already punched by other words.

    Why “no” is certain and “yes” is not

    Adding a word hashes it to seven positions and punches those seven holes. Nothing else is recorded: not the word, not its length, not which word punched which hole. 172,823 words went in at 9.59 bits each, 207 kB in all.

    Looking a word up hashes it the same way and checks the same seven holes. If one is blank, the word was never added, because adding it would have punched that hole. If all seven are punched, either this word punched them or other words did between them. The deck cannot tell those apart. That is the whole trade: a fixed, small amount of memory for an answer that is exact in one direction only.

    A hole cannot be unpunched, which is why a Bloom filter has no delete. And no working card ever looked like these. Machine rooms had a name for a card with every hole punched, a lace card; it was a prank, and it jammed the reader. A filter at its design size has half its holes punched, because that is where it tells strangers apart best.

    Stacked, the deck would stand 12.1 inches tall. The word list itself is 1.7 MB of text; punched eighty characters to a card it would need about 21,800 cards and stand over twelve feet.

    Burton H. Bloom, “Space/Time Trade-offs in Hash Coding with Allowable Errors”, Communications of the ACM 13(7), July 1970.

    The seven positions come from two hashes, after Adam Kirsch and Michael Mitzenmacher, “Less Hashing, Same Performance: Building a Better Bloom Filter”, 2006.

    Put one in front of something slow

    The usual place for a Bloom filter is in front of a lookup that costs something: a database, a cache miss, a call across a network. Ask the filter first. A no saves the trip. A yes means go and check.

    Strings are hashed as UTF-8 and numbers as little-endian bytes, so the same value always lands on the same holes. The usage guide covers key types, batches, snapshots and the sixteen hash strategies.

    using M5.BloomFilter;

var seen = FilterBuilder.Build(
    expectedElements: 1_000_000,
    errorRate: 0.01);

seen.Add("customer:42");
seen.Add(8675309L);

// A no is certain: skip the database.
if (!seen.Contains("customer:43"))
    return NotFound();

// A yes is a maybe: go and check.
var row = await db.FindAsync(id);

    New in 2.1

    Lookups no longer take a lock, and string, numeric and span keys are hashed without allocating. Three things are new: span keys, a reading of how full a filter is, and a way to combine filters built with the same settings.

    Nothing about hashing or saved filters changed, so 2.0 and 2.1 read each other’s snapshots.

    // One key from part of a buffer.
// No substring, no array.
bool hit = seen.ContainsKey(line.AsSpan(11, 11));
seen.AddKey(utf8Bytes);

// How full is it, really?
var now = seen.GetOccupancy();
if (now.EstimatedFalsePositiveRate > 0.02)
    RebuildLarger();

// Fill one filter per worker, then combine.
whole.UnionWith(shard);

    Snapshots that travel

    ToImmutable() returns a detached snapshot. The companion packages write it as JSON or protobuf together with its hash strategy, its sizes and a format version, so a reader can refuse bits it would misread. The file behind this page, words.json, is one of those snapshots.

    Versions 2.0 and 2.1 read each other’s files. Filters saved by 1.x have to be rebuilt from the original keys: version 2 changed hashing, and old bits under a new label would say no to keys that are there. The serialization guide has the protobuf and Newtonsoft.Json versions and the wire format.

    // M5.BloomFilter.Serialization.Json
var options = new JsonSerializerOptions();
options.Converters.Add(new BloomFilterConverter());

var json = JsonSerializer.Serialize(
    seen.ToImmutable(), options);

var restored = JsonSerializer
    .Deserialize<ReadOnlyFilter>(json, options);

    Do not fold, spindle or mutilate

    1. A yes is a maybe.

      Confirm it against the data that knows. A filter’s yes should never be the last word on anything that matters.

    2. There is no delete.

      A hole cannot be unpunched. When keys leave your set, build a new filter from the ones that remain.

    3. Overfilling is silent.

      Nothing throws when you pass the planned count. The false yeses just multiply. Check GetOccupancy().

    4. It is not a security control.

      The error rate assumes ordinary keys. Someone who picks keys on purpose can beat it. Do not use a filter to authorize anything.

    5. Bits do not explain themselves.

      A snapshot means nothing without its hash strategy, sizes and format version. Use the serializers; do not ship raw bits.

    6. Read the license.

      It needs .NET 10 and is source-available under PolyForm Strict 1.0.0, which is not an open-source license.

    Questions people ask

    What is M5.BloomFilter?

    M5.BloomFilter is a source-available C# Bloom filter library for .NET 10. It answers whether a key might be in a set using a compact array of bits instead of the keys themselves.

    Can a Bloom filter give a wrong answer?

    Only in one direction. A positive result means possibly present and can be a false positive. A negative result means definitely absent, provided the same filter, hash strategy and key encoding are used and the bits are intact. Confirm positive results against your source of truth.

    Does an error rate of 0.01 guarantee 1% false positives?

    No. The error rate is a sizing target for the expected number of keys, under the usual assumption that hashes spread keys evenly. Adding more keys than planned raises the rate. GetOccupancy() estimates the current rate from the bits that are actually set.

    Is the demonstration on this page the real library?

    The filter is. It was built by M5.BloomFilter in C# from the public-domain ENABLE word list and saved in the library's JSON format. The lookups run in your browser through a JavaScript port of the library's default hash, Murmur3KirschMitzenmacher, checked against the same test vectors as the C# code.

    Is it safe to use from several threads?

    Yes. Lookups take no lock, so any number of threads can query one filter at once. Insertions and snapshots share a lock. A lookup that starts after an insertion has finished always sees it.

    Can I read filters saved by an older version?

    Versions 2.0 and 2.1 read each other's snapshots. Filters saved by 1.x must be rebuilt from the original keys, because version 2 changed hashing; relabelling old bits as version 2 would produce false negatives.
